# AccountBank: роадмап нестандартных фич (персональный архив-банк)

Документ для передачи реализующему ИИ. Контекст: форк Telegram Desktop (tdesktop),
macOS arm64, 20–30 аккаунтов одного пользователя, цель — персональный архив-банк
собственных данных. Репозиторий: `/Users/dumay/Desktop/PaSEO/AccountBank`,
ветка `accountbank/bootstrap`. Референсы неофициальных клиентов: AyuGram Desktop,
64Gram, Materialgram, Forkgram, Graph Messenger, Swiftgram, NekoX/Nagram.

Правила стиля кода — в `AGENTS.md` и `REVIEW.md` корня репо (табы, `u"..."_q`,
минимум комментариев, `git log` — образец сообщений коммитов). В тексте ниже
якоря даются именами файлов и функций — номера строк намеренно не приводятся.

## 1. Принципы безопасности (обязательны для всех фич)

1. Своё api_id (уже есть в сборке). Никогда не публиковать и не менять на чужое.
2. Не ломать MTProto-инварианты: PFS, seq/pts/qts, ack; при гэпах — штатный
   `getDifference`. Читать все апдейты, не пропускать pts-гэпы.
3. Человеческие тайминги для любых активных действий: джиттер, никаких
   фиксированных интервалов и 24/7-активности на всех аккаунтах одновременно.
4. FLOOD_WAIT — экспоненциальный бэкофф, никаких долбёжек повторами.
5. Никаких массовых действий: mass-forward, рассылки незнакомцам, массовые
   join/add — главные документированные причины банов аккаунтов.
6. ToS-ломающие фичи (ghost, anti-recall, скрытие рекламы, автосейв
   самоуничтожающегося контента) — выключаемые per-account, не дефолт ON
   на всех 30 аккаунтах сразу.
7. Честный app_version в initConnection; маскировка под официальный клиент не нужна.
8. Локальные фичи серверу невидимы; риски создают только активные действия
   и нарушение протокольных инвариантов. Отправка сообщений по расписанию/ботом —
   единственная по-настоящему рискованная категория (средний/высокий риск).

## 3. Бэклог фич (по приоритету ценность/риск)

### F1. Локальный SQLite-архив всех сообщений — инфраструктура
**Ценность:** ядро банка; на ней строится F2, F3, F5, F6, F15.
**Прецедент:** AyuGram Desktop (свой SQLite), Materialgram (улучшенный экспорт).
**Что делает:** каждое входящее/исходящее сообщение, каждую правку и каждое
удаление сервера пишет в локальную БД `archive/<account>.sqlite` внутри workdir
аккаунта. Переживает перезапуск и чистку кэша.
**Реализация:**
- sqlite в зависимостях проекта НЕТ — подключить системный libsqlite3 macOS
  (`-lsqlite3`, чистый C API, ~100–150 строк обёртки; правки в `Telegram/cmake/`).
- Подписка на готовый rpl-продюсер `Session::newItemAdded()` (`data/data_session.h`)
  — нулевая инвазия в пайплайн; тонкие хуки в `Session::updateEditedMessage` и
  `Session::processMessagesDeleted` (оба в `data/data_session.cpp`).
- Таблицы: `messages(peer_id, msg_id, date, from_id, text, media_json)`,
  `deletions`, `edits`, `presence`, `reads`; дедуп по `(peer_id, msg_id)`.
- Писать сериализованное (`HistoryItem::originalText()`, from id, date),
  не указатели. Буферизованная запись (таймер-flush).
**Риски:** низкие (пассивный сбор апдейтов — штатный механизм).
**Критерии приёмки:** после просмотра 10 чатов в разных аккаунтах БД содержит
сообщения; перезапуск не дублирует записи; размер под контролем (лимит/ротация).
**Объём:** ~150–250 строк + cmake.

### F2. Anti-recall: сохранение удалённых сервером сообщений
**Ценность:** топ-1 УТП; ни один десктоп-форк не сохраняет медиа удалённых.
**Прецедент:** AyuGram Desktop (только текст — docs.ayugram.one/desktop/saving).
**Что делает:** при `updateDeleteMessages`/`updateDeleteChannelMessages` сообщение
не уничтожается, а помечается «удалено у отправителя» и остаётся в чате/архиве.
**Реализация:**
- Воронка: `Session::processMessagesDeleted` / `processNonChannelMessagesDeleted`
  (`data/data_session.cpp`) — при включённой опции вместо `item->destroy()`:
  сериализовать в БД F1 (фаза 1) и/или пометить side-set
  `base::flat_map<PeerId, base::flat_set<MsgId>> _serverDeleted` (фаза 2 — показ в чате).
- Флаги `MessageFlag` заняты все — side-set, не новый флаг.
- Артефакты для фазы 2: исключить «призрак» из `chatListMessage`/unreadCount,
  чистить set при выгрузке истории, идемпотентность к повторным пачкам getDifference,
  рендер серым/перечёркнутым по образцу `MessageFlag::SendingFailed`.
**Риски:** низкие (локально; AyuGram годами живёт).
**Критерии приёмки:** собеседник удаляет сообщение — оно остаётся в БД с меткой;
перезапуск не «воскрешает» уже удалённые; unread и превью чата не ломаются.
**Объём:** фаза 1 ~30–50 строк; фаза 2 ~80–150.

### F3. История редактирований сообщений
**Ценность:** вторая половина «банка неизменяемых данных».
**Прецедент:** AyuGram Desktop.
**Что делает:** каждое `updateEditMessage` сохраняет предыдущую версию
(текст + медиа-ссылку) в БД; UI-панель «версии сообщения».
**Реализация:** хук в начале `HistoryItem::applyEdition` (`history/history_item.cpp`)
до `setText`/`refreshMedia`; хранить снимок в компоненте БД (образец существующего
механизма: `HistoryMessageSavedMediaData::savePreviousMedia`, вызывается там же).
Дедуп по `editDate`; медиа — по слабым ссылкам/копированию файлов.
**Риски:** низкие. **Критерии приёмки:** правка сообщения пишет обе версии;
пачки правок после оффлайна не дублируются. **Объём:** ~60–100 + UI 150–300.

### F4. Ghost mode (читать без следов)
**Ценность:** банк на 30 аккаунтах не должен светить онлайн/прочитано/печатает.
**Прецедент:** AyuGram Desktop (полный ghost), Swiftgram.
**Что делает:** одна опция «Ghost mode» (Core::Settings, выключаемая per-account):
не отправлять read-receipts, не показывать онлайн, не слать «печатает»,
не помечать сторис прочитанными.
**Реализация (точки глушения сети, локальные пометки оставить):**
- «Прочитано» истории: `Histories::sendReadRequests` (`data/data_histories.cpp`)
  перед `sendRequest(RequestType::ReadInbox)`.
- «Прочитано» контента: `ApiWrap::markContentsRead` (`apiwrap.cpp`).
- Сторис: `Stories::markAsRead` (`data/data_stories.cpp`).
- Онлайн: `Updates::updateOnline` (`api/api_updates.cpp`), ветка isOnline.
- «Печатает»: `SendProgressManager::send` (`api/api_send_progress.cpp`).
**Подводные камни:** сервер пришлёт `updateReadHistoryInbox` со старым
still_unread_count при респине — гасить `applyInboxReadUpdate`, пока ghost включён;
view-once медиа завязано на read-апдейты (`checkSingleViewMediaBurn`) — не гасить
read для `isTtlCoveredMedia`; зацикливание онлайн-статуса себя (`gotOtherOffline`).
**Риски:** для аккаунта низкие; для api_id средние, если дефолт ON на всех —
делать выключаемым (прецедент: серверная санкция против api_id NekoX за input-status).
**Критерии приёмки:** при включённом ghost собеседник не видит «прочитано»/онлайн;
unread-счётчики у себя стабильны после переподключений; TTL-фото по-прежнему
сгорают у отправителя после просмотра (или это явно задокументировано как исключение).
**Объём:** ~60–100 строк.

### F5. Лог онлайн-статусов и изменений профилей
**Ценность:** мониторинговый блок, которого нет ни в одном десктоп-форке.
**Прецедент:** Graph Messenger (Contact Tracker / Special Contact / Contact Changes).
**Что делает:** пассивно логирует «кто когда был онлайн» и изменения
имени/юзернейма/текста контактов; просмотр в UI или экспорт.
**Реализация:** подписка на готовый `session().changes().peerUpdates(
Data::PeerUpdate::Flag::OnlineStatus)` (`data/data_changes.h`) — нулевая инвазия;
данные из `user->lastseen()` (`Data::LastseenStatus`). Писать в БД F1.
Буферизованный flush; только загруженные пиры; не поллить getFullUser для
сотен неконтактов (иначе scraping-паттерн).
**Риски:** низкие. **Критерии приёмки:** выход контакта в сеть пишется в лог
в течение секунды; нет лишних сетевых запросов (только пассивные апдейты).
**Объём:** ~40–80 строк. Отличная первая задача.

### F6. Лог «кто прочитал» (исходящие + просмотры сторис)
**Прецедент:** косвенно Plus Messenger (floating typing/online), Graph.
**Что делает:** лог «кто и когда прочитал мои сообщения/сторис».
**Реализация:** сообщения — `History::outboxRead` (`history/history.cpp`);
стоп-знак: в личных читатель = peer чата, в группах сервер даёт только
«read till max_id» — писать честно как диапазон. Сторис —
`Story::applyViewsSlice`/`applyViewsCounts` (`data/data_story.cpp`), там уже
распарсены `{peerId, date, reaction}`; доступны только для своих сторис.
Дедуп `(msgId, peerId)`; время StoryView.date — серверное, конвертировать.
**Риски:** низкие. **Объём:** ~60–100.

### F7. Автосейв view-once видео и TTL войсов
**Ценность:** закрыть последнее «сгорающее» медиа.
**Прецедент:** AyuGram Android (expire button); на десктопе — никто.
**Что делает:** одноразовое видео и войс с таймером копируются в `<загрузки>/ttl/`.
**Реализация:**
- Видео: новая `OverlayWidget::maybeAutoSaveTtlDocument()` по образцу
  document-ветки `maybeAutoSaveShownStory` (`media/view/media_view_overlay_widget.cpp`):
  условие `_document && media->document() == _document && media->ttlSeconds()`,
  затем `location(true)+accessEnable()+QFile::copy` или `document->save(fileOrigin(), toName)`.
  Вызовы рядом со всеми существующими вызовами `maybeAutoSaveTtlPhoto()`
  (displayPhoto, displayDocument, clearBeforeHide, подписка downloaderTaskFinished).
- Войс: в `history/view/media/history_view_document.cpp` в колбэке
  `TTLVoiceStops` перед `item->clearMediaAsExpired()` — копировать
  `_dataMedia->bytes()` в `ttl/ttl_doc_<documentId>.<ext>`.
**Подводные камни:** войс в overlay `Context::TTLViewer` идёт другой веткой —
проверить покрытие; `TTLVoiceStops` стреляет многократно — guard по файлу;
асинхронный `save()` должен успеть до burn (точки вызова уже до burn).
**Риски:** низкие-средние (ToS-формальность «preventing self-destruct»).
**Критерии приёмки:** просмотренное одноразовое видео и войс остаются в ttl/ после
сгорания в чате. **Объём:** ~100–130.

### F8. Скрытие спонсируемых сообщений

## 4. Распределение: что доверить другому ИИ, что делать самому

**Можно делегировать (изолированные точки, готовые якоря, низкий риск конфликтов):**
F5 (онлайн-лог), F8 (спонсорские), F7 (view-once видео/войс — по образцу
готовых maybeAutoSave*), F13 (QoL), F10 (экспорт), F15 (после F1).
Каждую фичу — отдельным коммитом, со сборкой `out-size-os` Release и
smoke-запуском с `-workdir` во временную папку (реальные сессии не трогать).

**Делать самому / под моим контролем (тонкие места синхронизации):**
F1 (инфраструктура SQLite + cmake), F2 (anti-recall — артефакты unread/chat-list),
F3 (правки — дедуп пачек), F4 (ghost — возвращающиеся unread, TTL-связка,
цикл онлайн-статуса), F9 (автозагрузка — объёмы).

**Не делать без отдельного решения:** массовые/активные действия
(рассылки, schedule-боты) — единственная категория с реальным риском банов.

## 6. Общие критерии готовности

- Сборка Release в `out-size-os` зелёная; smoke-запуск с временным `-workdir`
  стартует и останавливается чисто; реальные сессии не трогаются автоматикой.
- Ни одна фича не меняет MTProto-поведение по умолчанию без включённой опции.
- Новые настройки — через kv-prefs (`writePref/readPref`), не через двоичный стрим
  настроек (правила сериализации в AGENTS.md).
- Для упаковки: `ACCOUNTBANK_BUILD_TREE=out-size-os tools/package-test-release.command v<N>`
  (v15 занята; следующая v16). Профиль общий: `~/Library/Application Support/AccountBank`.
- Тестовый сценарий TTL/сторис/ghost проверяется вручную с другого аккаунта.
