# AccountBank v30: локальный архив и проверка производительности

Цель этого прохода: проверить текущий клиент macOS arm64, уменьшить задержки
архива и дать понятный просмотр удалённых сообщений, прежних версий и уже
сохранённых медиа. Исходный профиль, `tdata` и API-ключи не открывались.

## Независимые проверки

- Инженер производительности: массовое удаление запускало отдельную SQLite
  транзакцию для каждого сообщения; экспорт до 2 млн строк выполнялся в потоке
  интерфейса. При запуске до сих пор загружаются наборы стикеров и GIF для
  каждого аккаунта. Замеров с 20–30 аккаунтами нет.
- Инженер целостности данных: событие удаления содержит снимок только уже
  загруженного сообщения. Архив знает отправителя, исходную дату и время,
  когда клиент получил событие. Он не знает инициатора и точное серверное
  время удаления. Старые записи могут содержать только ID отправителя.
- Дизайнер интерфейса: один локальный просмотр с разделами для удалений,
  правок, сохранённых одноразовых фото и историй; облачный архив должен быть
  отдельно обозначен. Просмотр должен читать архив в фоне.

## Изменения

- Добавлен пункт меню `Deleted messages`. Окно переключается между четырьмя
  разделами: удаления, прежние версии, сохранённые одноразовые фото, истории.
- Показаны последние 50 записей каждого раздела. Для удаления и правки видны
  отправитель, чат, время обнаружения, примерный интервал после отправки и
  текст. Для медиа видны локальный путь и кнопка `Show in Finder`, только
  если файл ещё существует.
- Новые записи содержат имена отправителя и чата; формат старых записей
  остаётся читаемым. Сохранённые фото и истории записываются в архив лишь
  после успешного локального сохранения файла. Ранее сохранённые файлы
  автоматически в архив не импортируются. Асинхронное сохранение видеоистории
  пока не даёт гарантированного события успешного завершения.
- Массовое удаление пишет снимки одной SQLite транзакцией. Просмотр и экспорт
  читают базу через отдельное соединение в фоновом потоке. Экспорт остаётся
  атомарным JSON-файлом с правами только владельца.
- Повторный аудит выявил тяжёлую сортировку архива, неразличимую ошибку чтения
  и возможность запустить несколько экспортов в один файл. В фоновом потоке
  сортируются только ключи и метки времени, затем нужные записи читаются по
  ключу. Просмотр не меняет схему SQLite; ошибка чтения выводится отдельно,
  параллельный экспорт одного аккаунта блокируется.
- Разделы доступны явными ссылками вверху окна. Небольшие подписи и единицы
  времени используют локализацию приложения; формат даты — локаль macOS.
- При проверке потерянного ключа профиля вместо 29 временных объектов
  аккаунта используются проверки путей к файлам.

## Границы и проверки

- Это локальный архивный список, не серверный Telegram-чат. Приватный
  облачный канал для обычных правок/удалений из v27 остаётся отдельным пунктом.
  Одноразовые фото и истории в него автоматически не пересылаются.
- Время удаления означает «клиент обнаружил удаление». После офлайн-периода
  интервал может быть заметно завышен. Кто удалил сообщение, определить нельзя.
- Разделы медиа содержат ссылки на сохранённые файлы; архив SQLite не хранит
  байты фото или видео. Отсутствующий файл нельзя восстановить из списка.
- Для уже существующего файла запись добавляется при следующем просмотре;
  повторная запись того же пути не создаёт дубликат. Видеоистория, которую
  `DocumentData::save` завершает асинхронно, всё ещё может не попасть в список.
- Для раздела с редкими событиями фоновое чтение всё ещё может просмотреть и
  расшифровать много записей. На очень большом архиве первое открытие раздела
  может идти долго; операции чтения теперь не строят индекс и не удерживают
  блокировку записи из-за миграции схемы.
- Последние 50 записей читаются в фоне, но поиск более старых записей пока
  отсутствует. Для полного списка остаётся экспорт JSON.
- Нужно вручную проверить GUI на тестовом аккаунте: массовое удаление,
  перезапуск, старую запись без имени, одноразовое фото, историю, удалённый
  локальный файл и экспорт большого архива. Автотест или компиляция не
  подтверждают эти сценарии с реальным Telegram API.
- Производительность на 20–30 аккаунтах не измерена. Следующий отдельный
  проход: сравнить RAM/CPU при 1/5/10/20/30 аккаунтах, затем отключать
  загрузку неиспользуемых стикеров и реакций без изменения формата `tdata`.
