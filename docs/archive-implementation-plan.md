# F1: защищённый локальный архив — техническое решение до реализации

Статус: проект, **не реализовано**. Обычный SQLite-файл из дорожной карты нельзя подключать к 20–30 аккаунтам: текст, имена и медиа-ссылки останутся читаемыми после выхода из приложения. Оценка в 150–250 строк не покрывает криптографию, миграцию и жизненный цикл аккаунтов.

## Граница данных

- Архив принадлежит одному слоту аккаунта и лежит рядом с его локальным хранилищем. Никогда не открывать один SQLite-файл двумя процессами и не копировать живой `tdata` ради теста.
- Сохранять только обычные текстовые сообщения и разрешённые вложения. Медиа с TTL, view-once, protected/no-forward и платный закрытый контент не архивировать. Идентификаторы сообщения и отправителя сохранять внутри шифротекста; ключ поиска — HMAC от `(peer_id, msg_id)`.
- Исходные `TextWithEntities` и ID медиа сохранять без изменения серверных сообщений. Экран чата, unread, pts и `getDifference` не зависят от доступности архива.

## Формат и ключ

1. Ключ архива выводить из локального ключа **этого аккаунта** через HKDF-SHA-256 с отдельной меткой `AccountBank archive v1`. Не использовать Telegram transport auth key. Не печатать ключ или его производные в лог.
2. В SQLite записывать только версию формата, HMAC-индекс и AEAD-запись (`nonce`, `ciphertext`, `tag`). Для каждой записи — случайный nonce 96 бит и AES-256-GCM; тип записи и версия — authenticated associated data. Ошибка проверки tag означает отказ от чтения этой записи, а не пустое сообщение.
3. Вложения хранить отдельно только после отдельного решения о шифровании и бюджете диска. Первый рабочий срез — текст и метаданные обычного сообщения, без байтов медиа.
4. Для уменьшения утечки метаданных `page_size`, имена таблиц и количество записей остаются видимыми. Полное скрытие этих сведений требует шифрования страниц (например, SQLCipher), которого в текущих зависимостях нет. Не называть шифрование payload шифрованием всего файла.

## Запись и лимиты

- Одно подключение SQLite на аккаунт, открываемое только после успешной авторизации и закрываемое до уничтожения `Main::Session`. Все операции выполняются на одной сериализованной очереди; callback получения сообщения не блокирует UI на диске.
- Использовать prepared statements, транзакции пачками и `busy_timeout`; проверять каждый код возврата SQLite. Дедуп по HMAC-ключу сообщения. Сохранение edit/delete — отдельные версии, без подмены текущего сообщения.
- Предельный объём на аккаунт и суммарный предел на 30 аккаунтов задаются явно. При заполнении архива останавливать запись с видимым состоянием ошибки; не удалять старые данные молча.
- Не включать `secure_delete` как замену шифрованию. После падения WAL и временные файлы тоже должны содержать только шифротекст. Каталог `0700`, файлы `0600`; атомарные миграции и бэкап только в зашифрованном виде.

## Порядок реализации и проверки

1. Сначала отдельный модуль с синтетическим ключом и сообщениями: создать БД, записать, закрыть, открыть, проверить дедуп, неправильный ключ, повреждённый tag, WAL после аварийного завершения, права и лимит.
2. Затем вывести ключ из локального ключа аккаунта в `Storage::Account` и проверить жизненный цикл на **синтетических** профилях, включая смену локального пароля и удаление слота. Не читать рабочие сессии пользователя.
3. Только после этого подключить `Data::Session::newItemAdded()` и хуки edit/delete. Пустой или повреждённый архив не должен блокировать вход в Telegram и не должен менять server update processing.
4. Проверить GUI на 1/5/10/20/30 аккаунтах, startup/RSS/CPU/disk, выход и повторный вход. F2/F3/F5/F6/F15 начинать после приёмки F1.

Это решение оставляет важный выбор открытым: хранить только зашифрованные payload в системном SQLite или добавить SQLCipher и шифровать всю БД. До реализации сравнить размер бинаря, совместимость macOS и восстановление после повреждения для обоих вариантов.
