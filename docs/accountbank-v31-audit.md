# AccountBank v31 — быстрые правки, удаления и навигация по диалогам

## Задача и проверенный план

Роли независимой проверки: инженер MTProto, инженер целостности архива и
UX-редактор. Они проверяли код только в этом проекте; `tdata`, сессии и
API-данные не открывались.

1. Захватывать входящее сообщение при добавлении в `Data::Session`, даже если
   чат не открыт.
2. В одной SQLite-транзакции сохранять зашифрованное событие и индекс
   последней известной версии по паре «диалог, ID сообщения».
3. До применения правки сохранять пару «было → стало». Если сообщение уже
   выгружено, читать последнюю версию из локального архива.
4. При удалении искать прежний снимок даже без `HistoryItem` в памяти.
5. Дать русскую навигацию по диалогам и объяснить приблизительность времени.

## Что сделано

- Новые сообщения, проходящие через `Session::addNewMessage` как `Unread`,
  дополнительно передаются архиву. Существующий `newItemAdded` остаётся для
  других путей; соседние дубли в очереди отсекаются, а SQLite-ключ сообщения
  не допускает дублирования на диске.
- `state_index` хранит только HMAC-ключ и ключ зашифрованной записи, без второй
  копии содержимого. `nonchannel_index` связывает глобальный ID личного/обычного
  группового сообщения с последним снимком. Оба индекса обновляются в той же
  транзакции, что и событие.
- Правка записывает старый и новый текст, а также ID фото или документа после
  правки, если он есть в обновлении. Снимок делается до изменения
  `HistoryItem`. Если старый текст не известен, это явно видно в событии.
- Удаление сообщения вне памяти ищет последний известный снимок. Если клиент
  не видел исходное сообщение, событие с одним ID не засоряет ограниченный
  архив. Для загруженных сообщений прежнее поведение и отметка «удалено»
  сохранены.
- Окно архива переведено на русский. Из каждой записи можно перейти к событиям
  её диалога. Добавлены справка, подписи «Было/Стало», настройка видимости
  удалённых сообщений для всех диалогов и предупреждение о лимите архива.
- Облачное зеркало показывает имя чата, отправителя и тексты до/после, когда
  их удалось сохранить. Оно остаётся отдельным обычным каналом.

## Почему пока нет Telegram-топика на каждый диалог

По официальному [Telegram API для форумов](https://core.telegram.org/api/forum),
темы создаются в форум-группе, а текущий архив — broadcast-канал. Переход
потребует создать новую приватную megagroup с флагом `forum`, хранить
соответствие «диалог → ID темы», восстанавливать его после сбоев и ограничивать
частоту `messages.createForumTopic`/`messages.sendMessage`. Это отдельная
миграция облачного архива. Локальный архив уже даёт фильтр по диалогу и
остаётся основной копией при ошибках Telegram API.

## Пределы достоверности

- [Обновление удаления](https://core.telegram.org/constructor/updateDeleteMessages)
  содержит ID, но не текст и не личность удалившего. Если Mac был офлайн и
  исходное сообщение уже недоступно, восстановить его нельзя.
- Время события — момент получения обновления на этом Mac, а интервал от
  отправки приблизительный. После офлайна он может быть завышен.
- Новое сообщение обычно сбрасывается на диск с задержкой до 2 секунд.
  При быстрой правке или удалении в работающем клиенте очередь сбрасывается
  до записи события. Внезапное завершение до сброса может потерять снимок.
- Индексы v31 не покрывают все старые записи v30: для известного диалога есть
  поиск исходного сообщения по его прежнему ключу; для выгруженного личного
  сообщения без диалога старый снимок может остаться ненайденным. Если в v30
  сообщение уже редактировали, исходный снимок помечается как возможная старая
  версия, а не как точное состояние непосредственно перед новой правкой.
- Фильтр одного диалога на большом архиве ищет в фоновом потоке и может быть
  медленным. Показаны последние 50 совпадений; полный список даёт экспорт.
- Облачный канал не получает события, для которых текущие ограничения на
  сохранение контента не удалось проверить по загруженному сообщению.
